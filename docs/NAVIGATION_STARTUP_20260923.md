# 直达页面与初始化重跑：2026-09-23

线上验收曾观察到新标签页直达研究路径后返回首页；独立 Chrome 的普通加载却成功。
本次在本地真实 Streamlit 应用中复现了一个受时序影响的原因，并发现另一处会干扰切页的空存储重复回执。
没有取得当时线上 CUA 的 WebSocket 记录，因此不将所有浏览器问题归为同一原因；本文件记录本地修复验收，线上状态另由总发布记录确认。

## 有证据的原因

`main()` 原先先运行研究记录、游戏进度、设备偏好三个浏览器同步组件，再注册 `st.navigation`。
组件首次读取 localStorage 后调用 `setStateValue`，可以在目标页尚未注册时要求应用重跑。

测试包装器在组件之后增加一次受控等待，未改写页面、组件数据或浏览器请求：

| 导航注册前的等待 | 原代码研究页直达 | 调整顺序后 |
|---|---|---|
| 0 秒 | 研究页 | 研究页 |
| 0.1、0.5、1、2 秒 | 四次均回首页 | 四次均保留研究页 |

实际 WebSocket 消息显示：首请求的 `page_name` 是研究路径；早到的组件重跑却携带入口脚本哈希且无页面名；随后导航选择默认首页哈希。
零等待时导航消息先到，后续回传携带正确研究页哈希。该差异解释了普通加载成功而较慢初始化失败的现象。

修复仅将导航注册放在三个同步调用之前。三个同步函数保持原顺序，并仍在侧栏和目标页面执行前完成。

## 空案件回执

浏览器尚无案件记录时，JavaScript 读到 `null`，Python 则使用规范的全新空案件对象。
原组件在已确认存储可用后仍因二者序列化不同重复回传 `null`。浏览器实测中，这个旧页面回传曾覆盖已经请求的财务快照切页。
独立执行旧发布 `08216dd` 的原始组件也复现了重复回执，确认它并非本次调整初始化顺序才引入。

现在仅把“浏览器记录为空”与“内存为版本 0、无当前案件、无案件和命令记录的全新空对象”视为同一内容。
首次存储状态回执照常发送；较新版本、非空内存、无效浏览器记录、写入成功回执、写入失败和其他写入者冲突仍按原规则处理。
此修复不会创建、清空或覆盖用户的持久化案件。

- 新增 9 项真实 Streamlit AppTest：在三个同步边界分别强制一次重跑，检查首页、研究页和财务快照页保持目标且同步状态保留。修复前同类实验显示首页，修复后通过。
- 相关 Python 测试共 47 项通过；本节不是整仓测试计数。
- 案件存储 JavaScript 测试从 5 项增加到 10 项；新增的重复空回执用例修前失败、修后通过，已有写入与冲突测试继续通过。
